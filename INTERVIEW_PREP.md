# Orchestrate — Backend Interview Prep

> This is not a README recap. Each question targets a **specific decision in this codebase**. Practice saying the answer out loud, pointing at the exact file, function, variable, and value.
>
> **Stack:** Node.js ≥20, TypeScript, NestJS 11, BullMQ 5, Redis (`ioredis`), PostgreSQL + TypeORM, Docker Compose, Kubernetes (HPA + optional KEDA), Prometheus + Grafana + Alertmanager, worker libs (`fluent-ffmpeg`, `sharp`, `pdfkit`, `tesseract.js`, `nodemailer`, AWS S3 SDK).

# BASIC (50)

1. **What does Orchestrate do?** A multi-tenant background job orchestration system: clients submit jobs via a REST API; typed workers process them asynchronously through BullMQ queues on Redis; Postgres stores job state.
2. **Why split into API and workers at all?** Separation of concerns: the API stays responsive to HTTP while heavy/long CPU-bound work (video transcode, ML, PDF) runs in dedicated processes that can scale and fail independently.
3. **What language/framework is the API?** TypeScript + NestJS 11 (`api/`).
4. **What's the job queue library and version?** BullMQ `^5.66.5`.
5. **What backs the queues?** Redis (via `ioredis ^5.9.1`).
6. **What is the system of record for jobs?** PostgreSQL via TypeORM `^0.3.28` (the `jobs` table + related entities).
7. **What are the five worker types?** `media`, `ml`, `email`, `etl`, `report` — selected by the `WORKER_TYPE` env var (`workers/src/main.ts`, `VALID_TYPES`).
8. **What are the five queue names?** `media-jobs`, `ml-jobs`, `email-jobs`, `etl-jobs`, `report-jobs` (`QUEUE_MAP` in `queue.service.ts`).
9. **How does a job get submitted?** `POST /jobs` → `JobsController.createJob` → `JobsService.createAndEnqueue` → `TenantCapService.submitJob` → `QueueService.enqueue` → `queue.add(...)`.
10. **What HTTP endpoints exist for jobs?** `POST /jobs`, `GET /jobs`, `GET /jobs/:id`, `POST /jobs/:id/retry`, `POST /jobs/schedule`, `POST /jobs/list-recurring`, `POST /jobs/stop-recurring`, plus `POST /jobs/workflow` and `POST /jobs/batch`.
11. **How is auth handled in the API?** Global `JwtAuthGuard` + `RoleGuard` (set in `main.ts`); routes marked `@Public()` skip JWT; `@Roles('admin')` gates admin actions.
12. **What are the default job options for retries?** `retries: dto.retries ?? 3` (`jobs.service.ts`) → passed as BullMQ `attempts`.
13. **What backoff strategy is configured?** Exponential, base delay `2000` ms: `backoff: { type: "exponential", delay: 2000 }` in `queue.service.ts`.
14. **What is the DLQ and how is it named?** Dead-letter queue `${queueName}_DLQ` (e.g. `media-jobs_DLQ`); failed jobs that exhaust attempts are re-added there.
15. **What per-process worker concurrency do you use?** `concurrency: 1` (both base workers and dynamically registered workers). Scaling is by adding instances/pods, not raising concurrency.
16. **Where do metrics get exposed?** Each worker exposes metrics on `METRICS_PORT` (default `3001`); the API exposes `/metrics` and friends. Prometheus scrapes them.
17. **What monitoring stack is used?** Prometheus (scrape 15s) + Grafana (datasource → `http://prometheus:9090`) + Alertmanager.
18. **What container orchestration is used?** Kubernetes (manifests in `k8s/`, assembled via `kustomization.yaml`), plus Docker Compose for local/dev.
19. **What does `docker-compose.dev.yml` run?** Only infra: `redis` and `db` (Postgres) — you run API/workers on host during dev.
20. **What DB does the API talk to and how is it configured?** Postgres via env (`DB_HOST`, `DB_PASS`, etc.); `DB_HOST: postgres` in the k8s ConfigMap.
21. **What is `RUN_WORKERS_IN_API`?** A toggle in `app.module.ts`: only imports `WorkerModule` if `RUN_WORKERS_IN_API === "true"`. In prod it's `"false"` so workers run separately.
22. **What priority levels can a job have?** `HIGH`, `MEDIUM`, `LOW`, `NONE` (DTO enum); mapped to BullMQ numeric priorities `1, 2, 10, 20`.
23. **In BullMQ, does a lower or higher priority number run first?** Lower number = higher priority; so `HIGH=1` runs before `NONE=20`.
24. **What validation runs on the create-job DTO?** `class-validator` via global `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`): `priorityLevel` in the enum, `retries` 0–10, optional `delayMs ≥ 0`, optional `cron`, optional `idempotencyKey`.
25. **How do you schedule a delayed job?** Pass `delayMs`; `queue.service.ts` sets `options.delay = payload.delayMs`.
26. **How do you schedule a recurring job?** Pass a `cron` pattern; sets `options.repeat = { pattern, jobId: recurringJobId }`.
27. **How do you stop a recurring job?** `stopRecurringJob` finds the matching repeatable and calls `queue.removeRepeatableByKey(key)`.
28. **What does the media worker process?** `video_transcode`, `audio_transcode`, `image_resize` (`media-worker/processor.ts`), using `fluent-ffmpeg`/`sharp`.
29. **What does the ML worker process?** `text_summarization`, `classification`, `ocr` (uses `natural`, `tesseract.js`); `INFERENCE_TIMEOUT = 3000` ms, max input `10000` chars.
30. **What does the email worker do?** Validates recipients (syntax + Hunter API), sends via `nodemailer` SMTP, writes a `notifications` row with an idempotency reference.
31. **What does the ETL worker do?** Extract/transform/load via `ETLService`; supports `dependsOn` in metadata and can enqueue a `nextJob`.
32. **What does the report worker do?** Validates report payload, generates a PDF via `pdfkit`, enforces `MAX_FILE_SIZE_MB = 20`, uploads to local disk or S3.
33. **What's the JobStatus enum?** `QUEUED, PROCESSING, COMPLETED, FAILED, SCHEDULED, SKIPPED, PENDING, WAITING_FOR_DEPENDENCIES, READY, STAGED`.
34. **How does the API know which queue a job type goes to?** `QUEUE_MAP` / `resolveQueueName(type)` maps each job type string to its queue.
35. **What is the health endpoint?** `GET /health` (`health.controller.ts`) and `GET /metrics/health`.
36. **What's the Node version requirement?** `>=20.0.0` (root `package.json` engines).
37. **How does the API serve the dashboard?** Static assets mounted in `main.ts` at `/dashboard/`, plus `/processed_report/` and `/processed_media/`.
38. **What is `prom-client` used for?** Defining/collecting Prometheus metrics (queue depth, completed/failed counters, DLQ, durations, worker heartbeats) with prefix `jobque_`.
39. **How is CORS configured?** `CORS_ORIGIN` split by commas in `main.ts`.
40. **What is a BullMQ "attempt"?** One execution try of a job; `attempts=N` means up to N total tries before the job is considered failed.
41. **What Redis connection defaults do services use?** `host: REDIS_HOST || "redis"`, `port: REDIS_PORT || 6379` — consistent across queue, tenant-cap, and workers.
42. **Where is the DLQ move triggered?** In the worker's `failed` event handler in `base.worker.ts` (and `workerRegistry.service.ts`).
43. **What global exception handling does the API have?** `AllExceptionsFilter` returns `{ timestamp, path, error, stack }`.
44. **What is a "workflow" vs a "batch" job?** Workflow = DAG of dependent jobs (`POST /jobs/workflow`); batch = many independent jobs submitted together (`POST /jobs/batch`).
45. **What TypeScript strictness does the API use?** `strictNullChecks: true` but `noImplicitAny: false` (`api/tsconfig.json`); workers/shared use full `strict: true`.
46. **How many replicas does the API deployment start with?** `1` (with an HPA to scale up).
47. **How many replicas does media-worker start with?** `2` in `k8s/workers.yaml` (HPA min 1, max 10).
48. **What ports matter?** API `3001`, worker metrics `3001`, Redis `6379`, Postgres `5432`, Grafana `3002→3000`, Prometheus `9090`, Alertmanager `9093`.
49. **What is `idempotencyKey` used for?** Optional client-supplied key that becomes BullMQ `jobId` so a re-submission with the same key is deduplicated.
50. **What is `TenantCapService`?** Enforces a per-tenant max in-flight job cap (default 5); over-cap jobs are staged in Redis instead of enqueued.

# INTERMEDIATE (50)

1. **Explain running workers inside the API process vs separate containers, and why you chose separation.** `RUN_WORKERS_IN_API` can co-locate them (handy for local/dev), but prod sets it `"false"`. Separation gives independent scaling (media needs far more replicas than email), fault isolation (a crashing ffmpeg job doesn't take down the API), independent resource limits, and independent deploys.
2. **Trace the full enqueue path with the DB write.** `JobsService.createAndEnqueue` inserts a `jobs` row (`retries ?? 3`, `priorityLevel ?? "NONE"`, status `SCHEDULED` if `delayMs`/`cron` else `QUEUED`), resolves `queueName = resolveQueueName(type)`, then hands the payload to `TenantCapService.submitJob` which either enqueues or stages it.
3. **Explain exponential backoff: what does "2s base with 3 attempts" mean in real timing?** With `delay=2000`, `type=exponential`, `attempts=3`: attempt 1 immediate; retry after ~2000 ms; retry after ~4000 ms (2000·2^1). ~6s of backoff waiting across the three tries (plus processing time). After the 3rd failure the job is done and eligible for DLQ.
4. **What exactly triggers a move to the DLQ?** In the worker `failed` handler: `maxAttempts = job.opts.attempts ?? 5`; if `job.attemptsMade >= maxAttempts`, add the job to `${queueName}_DLQ`. So DLQ = "exhausted all retries".
5. **Where do `attempts`/`backoff` actually get set — worker or producer?** The **producer** (`queue.service.ts` `queue.add`) sets `attempts` and `backoff`. The worker config's `attempts`/`backoff` are commented out on purpose to avoid double configuration.
6. **How do chained/dependent jobs work in `createWorkFlow`?** It validates the DAG (jobs exist, unique keys, ≥1 root with no `dependsOn`, no cycles via DFS), then persists jobs as `READY` (no deps) or `WAITING_FOR_DEPENDENCIES`, and writes edges into the `job_dependencies` table.
7. **If Job B depends on Job A, what happens when A completes?** `onJobCompleted(A)` → `unlockChildren(A)`: for each child, count parents with `status != COMPLETED`; if `0` remain, set the child (and its dependency rows) to `READY`, then `scheduleNextJob` enqueues it.
8. **If Job A fails, what happens to B?** `BaseProcessor` catch path calls `chainService.handleParentFailure(A)`; for each child, if `faliureStrategy === "STRICT"` the child is marked `SKIPPED`; then `scheduleNextJob` runs. So strict dependencies cascade as skips rather than running B on bad input.
9. **Do you use BullMQ's FlowProducer for dependencies? Why or why not?** No — there's no `FlowProducer`. Dependencies are modeled in Postgres (`job_dependencies`) + custom unlock logic. Trade-off: full control, DB-visible DAG state, custom failure strategies; cost: you reimplement parent/child bookkeeping BullMQ Flows give for free.
10. **Explain the Kubernetes HPA for the media worker.** `autoscaling/v2` HPA, `minReplicas: 1`, `maxReplicas: 10`, metric = Resource CPU `averageUtilization: 75`. Scales media pods on CPU.
11. **Why does media get up to 10 replicas while others stay lower?** Media (video/audio transcode via ffmpeg, image resize via sharp) is the most CPU/time-intensive and bursty, so it needs the most headroom. ML max 5, email/etl/report max 4 — lighter, less bursty workloads.
12. **Give the HPA min/max for every worker.** media 1–10 (CPU 75), ml 1–5 (75), email 1–4 (70), etl 1–4 (70), report 1–4 (70); API 1–6 (70).
13. **What metric triggers scaling by default, and what's the alternative here?** Default HPA metric is CPU utilization. Alternative: the optional **KEDA** `ScaledObject` scales media-worker on **Redis queue depth** (`bull:media-jobs:wait` list length), min 1 max 15, threshold `listLength: 5`, polling 15s, cooldown 60s.
14. **Why is queue-depth scaling (KEDA) better than CPU scaling for a queue worker?** CPU lags the real signal — a backlog can build while CPU looks fine (I/O-bound waits). Queue depth directly reflects pending work, so KEDA reacts to backlog, not just CPU pressure.
15. **Why BullMQ over a plain Redis list (`LPUSH`/`BRPOP`)?** BullMQ gives you retries + exponential backoff, delayed/scheduled jobs, cron repeatables, per-job priority, atomic move-to-active with visibility/locks (so a crashed worker's job is reclaimed), completed/failed/stalled events, and queue introspection (waiting/active counts) for metrics and autoscaling. A raw list gives none of that — you'd hand-roll all of it and still lack atomic reliability guarantees.
16. **What BullMQ features do you actually use?** `attempts` + `backoff`, `priority`, `delay`, `repeat` (cron), `jobId` for idempotency, `QueueEvents`/worker events (`active`/`completed`/`failed`), and count APIs (`getWaitingCount`, etc.) for metrics.
17. **How does per-tenant concurrency capping work?** `TenantCapService`: `MAX_CONCURRENT_PER_TENANT = 5`. It `INCR`s `tenant:inflight:<tenantId>`; if `current <= 5` it enqueues (`QUEUED`); else it `DECR`s and `RPUSH`es the payload to `tenant:staging:<tenantId>` (status `STAGED`). On job release it drains staged jobs.
18. **Why cap per tenant at all?** Fairness/isolation in a multi-tenant system — one tenant submitting 10k jobs can't starve others of worker capacity; staging provides backpressure without dropping work.
19. **How does the "in-flight counter + staging list" get drained?** When a job finishes/releases, the service decrements the inflight counter and pops from the staging list to enqueue the next tenant job, keeping inflight ≤ cap.
20. **Why `concurrency: 1` per worker instead of a higher number?** Deterministic per-pod resource usage (one ffmpeg/OCR at a time), simpler autoscaling math (1 pod ≈ 1 concurrent job), and avoids one heavy job starving others in the same process. Horizontal scaling replaces vertical concurrency.
21. **How is idempotency enforced at the job level?** `jobs.idempotencyKey` is a unique DB column; and `queue.service.ts` only sets BullMQ `options.jobId` **when an idempotency key is provided** — deliberately not for every job.
22. **Why NOT set `jobId` to the DB uuid on every job?** The code comment explains: setting `jobId` on every job makes BullMQ **silently deduplicate** retries/re-submissions (same id = same job), breaking retry semantics. So `jobId` is reserved for explicit idempotency only.
23. **How does the email worker dedupe notifications?** `notifications` table has a unique `referenceId` and a unique composite index `(jobId, recipient, channel)` — so the same email can't be sent twice for the same job/recipient/channel.
24. **How does the ETL worker achieve load idempotency?** `upsert(transformedData, ["id"])` into `processed_users` — re-running the same load updates rather than duplicates rows.
25. **Explain graceful shutdown.** `WorkerRegistry.onModuleDestroy` calls `worker.close()` on all workers (BullMQ `close()` waits for in-flight jobs to finish before exiting), and metrics collectors clear intervals and close Redis/queue connections.
26. **Why does graceful shutdown matter with Kubernetes?** On pod termination (SIGTERM during rollout/scale-down), `worker.close()` lets the current job finish instead of being killed mid-transcode, avoiding partial output and unnecessary retries. Pair with a `terminationGracePeriodSeconds` longer than your max job time.
27. **How are metrics labeled?** Default labels `service` (worker|api) and `worker_type`; default Node metrics prefixed `jobque_nodejs_`; custom metrics prefixed `jobque_`.
28. **Which key metrics do you expose?** Queue depth gauge, completed/failed/retry counters, DLQ counters+gauge, job duration & wait histograms, worker heartbeat/count/active-jobs, autoscaler/band counters, tenant inflight/staged/cap-hit.
29. **What alerts are defined?** `TargetDown`, `HighJobFailureRate`, `DLQDepthHigh`/`DLQDepthCritical`, `WorkerHeartbeatMissing`, `APIHighErrorRate`, etc. (`monitoring/alerts.yml`).
30. **How does Prometheus discover targets?** Static scrape config in `monitoring/prometheus.yml`: `api:3001` and each worker `*:3001`, scrape interval 15s.
31. **How is the build/deploy artifact flow structured?** `shared` builds a `.tgz`; `workers` builds its own `.tgz` (also depended on by API); API installs both tarballs. That's why root scripts run `build:shared → build:workers → build:api`.
32. **Why does the API depend on the workers package (`@jobque/workers`)?** So the optional in-process worker mode (`RUN_WORKERS_IN_API=true`) can import `WorkerModule`; in prod it's off, but the dependency keeps a single source of processor code.
33. **Where do processed media/reports go?** Local dirs (`MEDIA_OUTPUT_DIR=/app/shared/media`, `REPORT_OUTPUT_DIR=/app/shared/reports`) or S3 when `USE_S3=true` (uses AWS SDK, `S3_BUCKET`).
34. **How do workers get the ffmpeg binary?** The workers Dockerfile installs ffmpeg and sets `FFMPEG_PATH=/usr/bin/ffmpeg` and `FFPROBE_PATH=/usr/bin/ffprobe`.
35. **Explain the Redis key schemes you rely on.** `tenant:inflight:<id>` and `tenant:staging:<id>` (capping), `jobs:<tenantId>:<minuteEpoch>` (per-minute rate limit, TTL 60s), `reconcile:queue:<name>:{pre_queue,terminal,totals}` (reconcile), and BullMQ's own `bull:<queue>:*` keys.
36. **What is the optional per-minute tenant rate limit in the worker?** If `TENANT_JOBS_PER_MINUTE > 0`, the worker `INCR`s `jobs:<tenant>:<minute>` (TTL 60s) and throws if it exceeds the limit — a second throttle layer beyond the concurrency cap. Default `0` = disabled.
37. **How is a job retried manually?** `POST /jobs/:id/retry` (admin) re-enqueues the job; distinct from BullMQ's automatic attempt-based retries.
38. **How do you list/stop recurring jobs via the API?** `POST /jobs/list-recurring` → `queue.getJobSchedulers()`; `POST /jobs/stop-recurring` → find repeatable by name/pattern/id and `removeRepeatableByKey`.
39. **What's the difference between `SCHEDULED`, `WAITING_FOR_DEPENDENCIES`, `READY`, and `STAGED`?** `SCHEDULED` = delayed/cron not yet due; `WAITING_FOR_DEPENDENCIES` = DAG parents incomplete; `READY` = deps satisfied, ready to enqueue; `STAGED` = held back by the tenant concurrency cap.
40. **How does the metrics reconcile flow detect drift?** `queueReconcileCollector` tracks counters (`pre_queue`, `terminal`, `totals`) so you can reconcile jobs entering vs terminal states and catch lost/stuck jobs; exposed via `GET /metrics/reconcile`.
41. **What resource requests/limits does media-worker get and why higher?** requests `cpu 500m / mem 512Mi`, limits `cpu 2 / mem 2Gi` — larger than other workers because transcoding is CPU+memory heavy. Email/report get `100m/256Mi` requests.
42. **How is the DB provisioned in k8s?** Postgres Deployment (replicas 1) with a `5Gi` PVC; Redis Deployment (replicas 1) with a `1Gi` PVC. (Talking point: single-replica stateful = SPOF; fine for demo, not HA.)
43. **What's in the ConfigMap vs the Secret?** ConfigMap: non-secret config (`RUN_WORKERS_IN_API`, `QUEUE_DEPTH_POLLER`, `DB_HOST`, `REDIS_HOST`, `USE_S3`, output dirs, `TENANT_JOBS_PER_MINUTE`, etc.). Secret: `JWT_SECRET`, `DB_PASS`, `AWS_*`, `S3_BUCKET`, `SMTP_*`, `GRAFANA_ADMIN_PASSWORD`, `SLACK_WEBHOOK_URL`, `HUNTER_API_KEY`.
44. **What do the kustomize overlays do?** `local-storage` swaps PVCs for hostPath volumes (`/var/lib/orchestrate/media|reports`); `minikube` sets `imagePullPolicy: IfNotPresent` and patches media-worker replicas to 1.
45. **How does role-based auth work on job creation?** `POST /jobs`, `POST /jobs/workflow`, `POST /jobs/batch`, `POST /jobs/:id/retry`, `POST /auth/create-users` are `@Roles('admin')`; the global `RoleGuard` reads `@Roles(...)` metadata and enforces it.
46. **What does batch job creation default retries to?** `3` (`batch-job.service.ts`), same as single jobs.
47. **How does the worker main process pick its type and fail fast?** `workers/src/main.ts` validates `WORKER_TYPE` against `VALID_TYPES` (`email|etl|media|ml|report`); an invalid/missing type aborts startup — prevents a misconfigured pod from silently doing nothing.
48. **How does `worker.module.ts` wire a type to a queue?** A map: media→`media-jobs`, report→`report-jobs`, ml→`ml-jobs`, email→`email-jobs`, etl→`etl-jobs`; only the matching worker class is instantiated for that pod.
49. **Why keep `removeOnComplete: false` / `removeOnFail: false` in the producer options?** To retain completed/failed job records in Redis for inspection, metrics, and debugging. (Trade-off: memory growth — see advanced Q.)
50. **What does `verify-m1.js` / the scripts do?** End-to-end verification: health + job lifecycle checks (poll 2000ms, timeout 120000ms); `deploy-k8s.sh` deploys an overlay and waits for rollouts; `verify-k8s.sh` port-forwards and runs `verify:m1`; `verify-monitoring.sh` curls Prom/Grafana.

# ADVANCED (50)

1. **Producer sets `attempts` but the worker's `failed` handler defaults `maxAttempts = job.opts.attempts ?? 5`. Where does the 5 ever apply, and is there a mismatch risk?** For jobs enqueued via `QueueService`, `job.opts.attempts` is always set (from `retries`), so the `?? 5` never triggers. It only matters for jobs added elsewhere without `attempts`. The subtle risk: DLQ logic and retry config live in different files — changing one without the other diverges behavior.
2. **`removeOnComplete/removeOnFail: false` keeps every job in Redis forever. What breaks at scale and how do you fix it?** Redis memory grows unbounded → eviction/OOM, slower BullMQ ops. Fix: `removeOnComplete: { age, count }` and `removeOnFail: { age }`, or a reaper that archives terminal jobs to Postgres (which is already the system of record) and trims Redis.
3. **You built a custom DAG in Postgres instead of BullMQ Flows. Defend it, then argue the other side.** For: DB-visible workflow state, custom failure strategies (`STRICT` skip), no coupling to BullMQ flow internals, queryable dependencies. Against: you reimplement atomic parent/child unlocking that Flows provide, risking races (see next Q), more code to maintain, and cross-store consistency (Postgres state vs Redis queue).
4. **Walk through a race in `unlockChildren` when two parents of the same child complete concurrently.** Both handlers query "parents with status != COMPLETED"; depending on timing both may see the other still non-complete (or both see zero and both enqueue the child). Without a transaction/lock the child can be enqueued twice or never. Fix: `SELECT ... FOR UPDATE` on the child, or atomic conditional update `UPDATE ... WHERE remaining_deps = 0`, or a DB-level dependency counter decremented atomically.
5. **Job state lives in both Postgres and Redis/BullMQ. How do you keep them consistent, and what's the failure window?** The enqueue is DB-write-then-Redis-add (or vice versa) without a distributed transaction, so a crash between them leaves a job row with no queued job (or vice versa). The reconcile collector exists precisely to detect this drift. Robust fix: transactional outbox — write job + outbox row in one DB tx, a relay enqueues to BullMQ, mark sent.
6. **`TenantCapService` does `INCR` then, if over cap, `DECR` + stage. Is this atomic? What's the race?** It's two round-trips: between reading `current` and staging, concurrent submits can both observe over-cap and over-decrement, or a release can interleave. Under contention inflight can drift from reality. Fix: a Lua script that atomically checks cap, increments or stages, and returns the decision.
7. **How can inflight counters leak (never decremented) and what's the operational impact?** If a worker crashes after `INCR` but before the release path runs (OOM kill, SIGKILL), `tenant:inflight:<id>` stays elevated forever, permanently shrinking that tenant's effective cap until manual reset. Mitigate with TTL on the counter + periodic reconcile, or derive inflight from BullMQ active counts instead of a separate counter.
8. **Compare CPU-based HPA vs KEDA queue-depth scaling for media. When does each misbehave?** CPU HPA under-scales I/O-bound backlogs and over-scales on GC/warmup spikes. KEDA on `bull:media-jobs:wait` reacts to backlog but can thrash if threshold (5) is too low or cooldown (60s) too short, and it ignores per-job cost variance. Ideal: KEDA on queue depth + a max cap, with cooldown tuned to job duration.
9. **KEDA scales media to max 15 but the HPA max is 10 and the deployment starts at 2. What conflict can arise from running both?** Two autoscalers fighting over the same Deployment's replica count causes flapping. You should run KEDA **or** the HPA for a given target (KEDA actually manages an HPA under the hood). Pick one authority; if KEDA, remove the plain HPA on media-worker.
10. **`concurrency: 1` + horizontal pods: what's the scheduling inefficiency and when would higher concurrency win?** For I/O-bound work (email, S3 upload, HTTP OCR calls) a single job per pod wastes CPU while waiting; higher concurrency would pack more throughput per pod cheaply. `concurrency: 1` is right for CPU-bound ffmpeg but wasteful for email/etl — consider per-worker-type concurrency.
11. **Explain exactly how BullMQ guarantees a crashed worker's in-flight job isn't lost, and what a raw Redis list can't do here.** BullMQ atomically moves a job to the active set with a lock/lease; a stalled-job checker returns jobs whose lock expired back to waiting. A raw `BRPOP` pops the item off the list — if the worker dies, the item is gone. That reliability is a core reason to use BullMQ.
12. **The stalled-job/lock mechanism can cause double processing. How, and how do you make processors safe?** If a job runs longer than the lock/stall timeout, BullMQ may consider it stalled and re-deliver it while the original still runs → at-least-once, not exactly-once. Make processors idempotent (the email unique index, ETL upsert do this) and/or extend lock duration for long jobs.
13. **Design idempotency for the media worker (which currently has none like email/ETL do).** Derive a deterministic output key from input hash + job params; check object store before transcoding; write to a temp path then atomic rename; record a completed marker keyed by job idempotency key so a re-delivery short-circuits.
14. **`options.jobId = idempotencyKey` dedupes submissions — but what happens if a client reuses a key after the first job completed and was NOT removed?** With `removeOnComplete: false`, the old job id still exists, so BullMQ won't add a new job with the same id → the "new" submission is silently dropped. Reusing keys is unsafe unless you scope them (e.g. include a date) or remove terminal jobs.
15. **The email worker calls the Hunter API to validate recipients. What are the failure/latency/cost risks and mitigations?** External dependency on the hot path: latency, rate limits, cost per check, and outages block sends. `HUNTER_SKIP_VERIFY=true` bypasses it. Mitigate: cache verification results, make it non-blocking/best-effort, circuit-break, and fall back to syntax-only on Hunter failure.
16. **ML worker has `INFERENCE_TIMEOUT=3000ms` and max input 10000 chars. How is the timeout enforced and what if the model call ignores it?** It must be enforced by racing the inference against a timer (`Promise.race`) or an abort signal; if the underlying library ignores cancellation, the promise rejects but the work continues consuming CPU. True cancellation needs a killable subprocess/worker thread.
17. **How would you prevent one giant video job from monopolizing a media pod for an hour and blocking the queue?** With `concurrency: 1`, a long job blocks that pod entirely. Options: enforce max job duration + chunked/segmented transcoding, route large media to a separate high-resource queue, or use BullMQ rate limiting + more replicas so backlog drains on other pods.
18. **DLQ jobs are added with `removeOnComplete/Fail: false` and nothing consumes the DLQ. What's the lifecycle problem and a proper DLQ strategy?** The DLQ just accumulates forever with no reprocessing path. Proper: a DLQ inspector/replayer (manual or automated with capped re-attempts), alerting on `DLQDepthHigh/Critical` (already defined), retention/TTL, and a triage dashboard.
19. **Poison-pill job: a deterministically-failing job retries 3× then DLQs. How do you distinguish a poison pill from a transient outage in your alerts?** Transient outages spike `HighJobFailureRate` across many jobs simultaneously and recover; a poison pill is a single job repeatedly failing. Differentiate by per-job failure attribution + DLQ growth rate vs overall failure rate; only page on sustained/broad failure, not single-job DLQ entries.
20. **Explain the thundering-herd risk when many delayed/cron jobs fire at the same timestamp, and how BullMQ + your setup handle it.** All become ready simultaneously → spike. BullMQ's delayed set promotes them to waiting at due time; your throttles (tenant cap 5, optional per-minute limit, `concurrency:1` × replicas) bound execution. Add jitter to cron/delays and rely on KEDA to scale on the resulting queue depth.
21. **Postgres and Redis are single-replica in k8s. Enumerate the SPOFs and the HA design.** Redis down = no queue = no processing; Postgres down = no job state. HA: Redis Sentinel/Cluster or managed Redis, Postgres primary+replica with failover (or managed RDS/CloudSQL), PVCs on durable storage, PodDisruptionBudgets, and BullMQ reconnection/backoff.
22. **`RUN_WORKERS_IN_API` co-location: name three concrete production problems it causes.** (1) A CPU-bound transcode starves the event loop → API latency spikes; (2) you can't scale API and workers independently; (3) a worker crash/OOM takes down HTTP serving. Hence `"false"` in prod.
23. **How does back-pressure propagate from an overloaded media queue back to clients?** It mostly doesn't at HTTP time — `POST /jobs` returns quickly after enqueue/stage; backlog is absorbed in Redis + staging lists. Explicit back-pressure would require rejecting/429-ing when queue depth or tenant staging exceeds a threshold. Good "what I'd add" answer.
24. **Two API replicas both run queue-depth pollers / cron schedulers. What duplication risk exists and how to fix?** Duplicate recurring-job registration or duplicate polling/metrics. Fix: elect a single leader (Redis lock / k8s Lease) for scheduler/poller responsibilities, or run them as a singleton Deployment (replicas 1) separate from the scalable API.
25. **The reconcile counters are Redis keys. What happens on Redis flush/restart and how reliable is reconciliation then?** Counters reset, so reconciliation loses history and may report false drift after a Redis restart. For durable reconciliation, source truth from Postgres job states and treat Redis counters as a fast cache, or persist snapshots.
26. **Priority is set at enqueue time; a low-priority job already waiting won't be preempted by a new HIGH job on a busy `concurrency:1` worker. Explain and mitigate.** BullMQ priority orders the waiting set, not running jobs — no preemption. A long LOW job blocks a newly-arrived HIGH job on that pod. Mitigate with separate queues/pools per priority, shorter jobs, or more replicas so HIGH gets a free worker.
27. **`bullPriorityOverride` from "branch rank" in workflows — why compute priority from DAG position?** To keep a workflow's jobs progressing in dependency order and prevent later branches from starving earlier critical-path jobs; branch rank maps DAG depth/criticality to BullMQ priority so the queue respects workflow topology, not just submission order.
28. **How would you implement exactly-once side effects for email given at-least-once delivery?** You can't get exactly-once delivery, only exactly-once *effect*: the unique `(jobId, recipient, channel)` index + `referenceId` make the DB insert the dedupe point — attempt to insert the notification row before/transactionally-with sending; on duplicate key, skip the send. That's the pattern already in place.
29. **The workflow uses `faliureStrategy === "STRICT"` to skip children. Design the non-strict strategies and their semantics.** e.g. `CONTINUE` (run child anyway, parent output optional), `RETRY_PARENT` (re-attempt A before failing B), `PARTIAL` (run child if a quorum of parents succeeded). Each needs clear rules for what data the child receives when a parent didn't complete.
30. **How do you cancel an in-progress workflow (kill switch)?** Mark the workflow cancelled in Postgres, set remaining jobs to `SKIPPED`, remove not-yet-active BullMQ jobs (`queue.remove`/drain), and signal running processors to abort (cooperative cancellation via a checked flag). BullMQ can't force-kill a running processor, so processors must poll for cancellation.
31. **Redis has no logical DB separation configured. What's the risk of sharing one Redis for BullMQ + tenant caps + reconcile + rate limits?** Key namespace collisions, one workload's memory pressure/eviction affecting queues, and `FLUSHDB` blast radius. Mitigate: separate Redis instances/DBs for queue vs app state, consistent key prefixes (already used), and `maxmemory-policy` that never evicts BullMQ keys.
32. **Walk through what happens to `STAGED` jobs if the API restarts. Are they safe?** They live in the Redis `tenant:staging:<id>` list, so they survive an API restart. But if the drain logic only runs on job-release events, staged jobs can stall until the next release. A periodic drainer / on-startup reconcile is needed to avoid stuck STAGED jobs.
33. **`noImplicitAny: false` in the API tsconfig — what class of bugs does that let through and why might it matter for a queue payload?** Untyped `any` payloads mean malformed job data (`job.data`) isn't caught at compile time; a missing `tenantId` or wrong field type surfaces only at runtime in a worker. Tighten with `strict: true` (workers/shared already use it) and validate `job.data` at processor entry.
34. **How would you add distributed tracing across API → Redis → worker → S3?** Propagate a trace/span id in the job payload; workers start a child span on `execute`; instrument with OpenTelemetry, export to a collector, correlate with the `jobque_` Prometheus metrics via exemplars. Enables end-to-end latency attribution per job.
35. **The media/report workers write to `/app/shared/media` (a PVC) or S3. What are the multi-replica consistency concerns with the PVC path?** A shared `ReadWriteOnce` PVC can't be mounted by many pods across nodes; concurrent writers risk partial files/name collisions. S3 (with atomic object writes + unique keys) is the correct multi-replica choice — which is why `USE_S3=true` is set in the ConfigMap.
36. **Design job result storage/retrieval so `GET /jobs/:id` scales and doesn't hammer Redis.** Store terminal results/metadata in Postgres (system of record); serve `GET /jobs/:id` from Postgres with indexes on `(tenantId, id)` and `(tenantId, status, createdAt)`; keep Redis only for live queue state. Avoid scanning BullMQ for historical jobs.
37. **How do you prevent a tenant from starving others even within the cap of 5, given jobs vary wildly in cost?** A count-based cap treats a 2h transcode like a 1s email. Add weighted capping (cost/credits per job type), separate per-type quotas, or fair-share scheduling (round-robin across tenants at dequeue). Pure count fairness is coarse.
38. **Explain the exact retry timing including BullMQ's backoff jitter (or lack thereof).** Default exponential backoff is deterministic: `delay * 2^(attemptsMade-1)` → 2s, 4s. No jitter by default, so many jobs failing together retry in lockstep (thundering herd on the downstream). Add a custom backoff function with jitter for shared-dependency failures.
39. **If the downstream (SMTP/S3/DB) is down, all jobs fail and DLQ fills after 3 attempts in ~6s. Why is that bad and what's the fix?** A brief outage permanently dead-letters a flood of legitimate jobs. Fix: circuit breaker to pause the queue (`queue.pause()`) on downstream outage, longer/again-scheduled backoff for infra errors, and distinguish retryable (5xx/network) from non-retryable (validation) failures so only true poison pills DLQ.
40. **How would you implement a "drain and redeploy" for workers with zero job loss during a k8s rolling update?** SIGTERM → stop accepting new jobs (`worker.close()` stops fetching) → finish in-flight → exit; set `terminationGracePeriodSeconds > maxJobDuration`; use `maxUnavailable`/surge so capacity stays up; BullMQ re-queues anything not acked. Verify with the `failed`/stalled handling.
41. **Metrics endpoints (`/metrics`, `/metrics/queues`, etc.) appear public. What's the risk and mitigation?** They leak operational internals (queue depths, tenant counts) and add scrape load; if truly `@Public` they're unauthenticated. Mitigate: bind metrics to an internal-only port/NetworkPolicy, scrape via cluster-internal service, and keep business metrics tenant-anonymized.
42. **The `job_dependencies` DAG validation does cycle detection via DFS at creation. What's the complexity and failure mode for very large workflows?** O(V+E) DFS in memory at submit time; for huge DAGs it's a single large request that can time out or use lots of memory, and it validates only at creation (runtime edges can't be added safely). Consider streaming validation, size limits, and topological batching.
43. **How do you guarantee a recurring (cron) job isn't registered multiple times across API replicas?** BullMQ repeatables are keyed (pattern + `recurringJobId`), so identical registration is idempotent — but differing `recurringJobId`s create duplicates. Enforce a canonical repeat key and single-leader registration; audit with `getJobSchedulers()`.
44. **Explain the memory/perf cost of keeping `QueueEvents` + worker event listeners on every worker, and when it bites.** Each `QueueEvents` opens its own Redis connection and streams all queue events; with many queues/replicas that's many connections and event traffic. At scale, consolidate event listening (dedicated metrics service) rather than per-worker `QueueEvents`.
45. **A job's `retries` can be 0–10 (DTO). What breaks at `retries: 0` vs the DLQ logic?** `attempts: 0` is invalid/edge for BullMQ (min 1 effective); and DLQ triggers on `attemptsMade >= maxAttempts`, so with 1 attempt a first failure immediately DLQs. Validate min 1, and document that low retries + infra blips = fast DLQ.
46. **How would you make the tenant cap and rate limits configurable per tenant instead of the global `MAX_CONCURRENT_PER_TENANT = 5`?** Store per-tenant limits in Postgres/Redis (plan-based), load them in `TenantCapService`, cache with TTL, and fall back to the global default. Enables premium tenants higher concurrency — the current hardcoded 5 doesn't.
47. **The worker rate-limit key is `jobs:<tenant>:<minute>` with fixed 60s windows. What's the boundary problem and a better algorithm?** Fixed windows allow up to 2× the limit across a window boundary (burst at :59 and :00). Use a sliding-window counter or token bucket in Redis (Lua) for smoother limiting.
48. **Design multi-region / DR for this system.** Active-passive: replicate Postgres cross-region, run workers in-region against a regional Redis (queues are region-local — don't stretch Redis across regions due to latency), fail over API + promote DB replica, and reconcile in-flight jobs from Postgres on failover. Discuss why stretching a single BullMQ/Redis across regions is a bad idea (latency, split-brain).
49. **How do you test the parent-child unlock and failure-cascade logic deterministically?** Integration tests with a real Redis+Postgres (testcontainers): submit A→B, force A complete → assert B becomes `READY` and enqueues; force A fail with STRICT → assert B `SKIPPED`; add a concurrency test firing two parents' completions in parallel to catch the unlock race.
50. **"What would you refactor first for production?" — give a prioritized, code-grounded list.** (1) Make tenant cap + inflight atomic (Lua) and TTL the counter to prevent leaks; (2) add job retention (`removeOnComplete/Fail` with age/count) + a DLQ replayer/alerting; (3) transactional outbox for Postgres↔BullMQ consistency; (4) pick one autoscaler (KEDA queue-depth) for media, remove the conflicting HPA; (5) idempotency for media/report processors + safe `idempotencyKey` reuse; (6) fix workflow unlock races with DB-level atomic dependency counters; (7) HA Redis/Postgres; (8) `strict: true` + validate `job.data` at processor entry; (9) leader election for schedulers/pollers; (10) jitter + retryable-vs-fatal classification in backoff.
